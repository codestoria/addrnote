# Content and deployment maintenance

## Content model and routes

The manifest supports three shapes: a standalone unit, a collection of units, and a section containing groups of units. Add new categories to the content manifest and create the corresponding index pages in both locale trees. Each slug and source directory must be a single safe path segment, and each title must be nonempty in every locale. Names ignored by the scanner (including dot-prefixed and underscore-prefixed names, `dist`, and `node_modules`) are rejected in the manifest. Add notes inside a registered unit; the sidebar scanner discovers them automatically. A different hierarchy requires changes to the manifest projection, navigation tree, and publication policy. Keep the three existing shapes until another hierarchy is actually needed. For a new hierarchy, update the manifest types and `getContentUnits`, navigation projection in `content/tree.ts`, publication policy in `scripts/lib/publication.ts`, route rules, validation, and synthetic tests together. To hide a registered section from navigation without changing publication, add its slug to `HIDDEN_NAVIGATION_SECTIONS` in `content/navigation.ts`; its content and unit sidebars remain available. Publication additions are configured separately in `content/publication.ts`.

Every section, group, collection unit, and content directory uses a two-digit `NN-name` source directory. Set `directory` on every manifest entry: removing the two-digit prefix must yield its `slug` (for example, `01-guide` and `guide`). The directory controls sorting and source paths; the slug forms the public URL. Keep sibling numbers unique. The generated route rules strip prefixes for registered structural directories and the nested depths configured by each section. Changing a rule changes the corresponding public URLs. Sidebar labels use the localized title or a normalized name.

## Publication and translations

Strict generation checks publication coverage, required indexes, rewritten route collisions, metadata, and matching locale-relative paths. Mirror checking includes hidden files and non-Markdown assets, without name-based exclusions inside locale trees. Keep build artifacts outside the locale trees. It does not compare file contents or verify translations.

Strict validation requires every directory inside a locale tree to use `NN-name` with exactly two digits and rejects duplicate numbers among siblings. Rename paths in both locales together, update the manifest, and check source-to-public route mapping before publishing. Locale root names themselves remain `zh` and `en`.

`translation: pending` blocks publication; missing status remains permitted for unmarked pages. Before publishing new or changed translations, run `npm run translation:audit`, review both language versions and their frontmatter, and resolve findings for those changes. This command exits nonzero while any page lacks `translation: complete`; review the content before adding that marker. For focused review, run `npm run translation:audit -- --changed` to check pages changed against `HEAD`, including staged, unstaged and untracked files, while still checking the complete mirror structure. Pass a Git base ref after `--changed` to compare with another revision (for example, the target branch in CI). Deleted pages are excluded from marker checks; mirror validation still detects asymmetric deletion. The command reports how many existing locale pages it checked, including zero. It checks markers, not the quality of a translation.

Default publication coverage is derived from registered content units, independently of navigation. Use `PUBLICATION_ADDITIONS` for extra published paths, or supply an explicit publication policy when callers need different coverage. New and renamed pages must be mirrored in each locale to pass strict generation.

## Compatibility and migration

The default-theme CSS selectors, navigation component integration, and VitePress `resolvePages` call are compatibility boundaries. On a VitePress upgrade, run the synthetic page-discovery and sidebar tests and manually inspect theme rendering and interaction. The test suite checks reusable functions and integration contracts independently of the current theme.

When moving the site, check `SOURCE_DIRECTORY`, `SITE_BASE`, `REPOSITORY_URL`, `DEFAULT_BRANCH`, the Pages workflow artifact path and branch condition, and Node versions in both `package.json` and the workflow. Verify the generated routes, edit links, and deployed asset paths. Keep the Pages artifact upload and deployment permissions aligned with the hosting configuration. The deployment test checks the repository-path Pages settings, workflow branch, artifact path, and Node minimum; update that contract deliberately when changing hosting mode.
